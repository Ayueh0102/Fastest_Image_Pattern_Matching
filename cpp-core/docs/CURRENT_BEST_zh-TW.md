# 目前建議使用的方案

更新：2026-10-24，Apple M4 Pro／48 GiB。這是依已測場景選型的指南，不是通用最快或完整實拍驗收證明。第一次閱讀請先看[專案導覽](../../docs/PROJECT_GUIDE_zh-TW.md)。第1–34輪詳細數字已移至[歷史建議](CURRENT_BEST_HISTORY_zh-TW.md)，避免把當年的「下一步」誤認成現在的待辦。

## 依使用場景選擇

| 使用情境 | 目前建議 | 採用界線與依據 |
|---|---|---|
| 一般灰階模板比對／Qt GUI | 先使用既有 CPU 基準與已實作旋轉、金字塔、subpixel | 穩定核心是固定尺度；需要尺度時選原生研究流程。GUI 預設未被實驗自動改動 |
| 大量相同模板、多尺度 | Metal 前段＋resident0精修、u8／shared、fine strip＋融合 | 第34輪同前段 CPU／Metal 公平比較，128／512物件完整時間約快12%／15%；不是全GPU |
| 完整解析度 subpixel 細搜尋 | 在上述組合評估精確角度重用 | 第29／30輪有收益；快速 stopLayer1 不一定重用得到 |
| 小圖／少候選／小模板精修 | 保留 CPU 精修選項 | GPU 啟動與同步可能超過計算收益，不能單由圖大小決定後端 |
| 固定尺度、角度改變、大圖稀疏目標 | 可試方向特徵稀疏研究路徑＋Metal前段 | 第20輪4K優勢明顯；小圖仍CPU較快。這條路徑與金字塔模式分開比較 |
| 很小的細紋模板，旋轉後漏搜 | 先限制金字塔深度，檢查粗搜尋候選 | 第35輪發現43×30模板縮到11×8時漏搜；不能只降低最終接受分數。完整結果見第35輪報告 |
| 定位後找顏色不同的物件 | RGB NCC與線性色度為研究選項 | RGB NCC不保證異色可分；色度會受白平衡影響，實拍漏搜也無法由後段修復 |
| 粗搜尋正規化與選峰留在GPU | `coarse_peak_mode=2`僅供研究，維持`1`為建議值 | 第36輪8K少物件快26.4%，128／512物件耗時約6／11倍；完整源碼與失敗保留 |
| 完整灰階搜尋留在GPU | 研究設定選`full_gpu=true, full_gpu_peak_mode=1, full_gpu_fine_mode=4` | [第40輪](GPU_NCC_CLOSURE_zh-TW.md)：128／512對本輪GPU基線再少16.3%／15.4%；128接近混合，512仍比混合多17.3%時間，8K少物件GPU有明顯優勢；不含RGB與稀疏路徑 |
| 大量相同物件、可接受輸出不逐位相同 | 研究選項`candidate_dedup_top_k=3`（radius 0.5、angle_steps 3），混合或完整GPU皆可 | [第43輪](CANDIDATE_DEDUP_zh-TW.md)：本輪112／79個GT案例變體零GT退步，128／512物件混合少30.4%／37.0%、完整GPU少26.1%／25.7%；會改變語意，matches不保證與基線相同。k1會失去物件；對稱週期小於3個粗角度步的模板未驗證。預設仍為0 |
| 同模板持續輸入新影格 | `Session::updateSource` | 保留模板與frame容量，每個Session同時只供一位呼叫者；不是直接重用舊影格金字塔。混合每次換影格會重建pose context（[第41輪](NEW_FRAME_COST_zh-TW.md)128約20ms、512約40ms） |

> 2026-10-19更正：上表完整GPU對混合的比較中，混合正式呼叫重用首次建立的pose context；加回後fine4在128約快4%，512仍以混合較快。8K是常數背景上6個0°、尺度1的完全複本，屬精度鑑別力低的速度負載。見[第40輪報告文末更正](GPU_NCC_CLOSURE_zh-TW.md)。

> 2026-10-19第41輪實測：每次呼叫都換新影格（`updateSource`）時，fine4對混合每影格為128 −6.9%、512 +13.7%、六物件 +13.3%、8K −70.2%，各6個block同向，上一則估算的方向成立。持續輸入新影格時依此工作量選擇；預設不變。見[每影格成本](NEW_FRAME_COST_zh-TW.md)。

## 大量物件的原生研究設定

下列是第32／34輪支持的手動組合，鍵名採研究 runner JSON。它們不是 GUI 已自動啟用的預設，也沒有自動選型門檻。

```json
{
  "backend": 1,
  "refinement_backend": 1,
  "pose_resident_mode": 0,
  "pose_input_mode": 1,
  "pose_storage_mode": 1,
  "ncc_mode": 2,
  "coarse_peak_mode": 1,
  "fine_ncc_mode": 2,
  "fine_fused": true,
  "fine_angle_reuse": true,
  "overlap_enabled": false
}
```

尺度清單、角度範圍、模板大小、候選預算與接受分數仍須依任務設定。不同位置的 mode2 指不同功能：粗NCC空間重用、fine點積載入重用與resident SIMD精修不能混為一談。多尺度目前保留resident0；不能直接把固定尺度稀疏路徑的resident2優勢外推。

`pose_input_mode=1`減少初始化float暫存；`pose_storage_mode=1`共用CPU／Metal影像頁面。這是記憶體改善，不能把兩個不同輪次的加速率相乘。GPU共用頁面也不能再加到RSS，當成另一份實體記憶體。

## 本輪的採用判斷

第41輪[每換一張影格的成本](NEW_FRAME_COST_zh-TW.md)只做量測：每次呼叫都經過`updateSource`時，fine4在128為808.35ms、比混合868.05ms快6.9%，512為2806.40ms、比混合2467.33ms慢13.7%，各6/6 block同向；六物件慢13.3%、8K快70.2%。混合每影格重建pose context中位19.94／40.19ms，另有候選搜尋的額外時間。96程序、1008次直接GT零FP／FN；不改GUI或通用預設，fine4仍是明確研究選項。

第40輪[精確NCC與大階段結案](GPU_NCC_CLOSURE_zh-TW.md)完成有界uint32、來源統計滑動重用與SIMD32比較。GPU研究推薦peak1／fine4，完整時間128為806.46ms、512為2805.18ms；命名GPU配置不增加。統計重用mode3較慢，保留源碼與失敗。562次直接GT零FP／FN、GPU有序結果一致，Release70／70、五分鐘108次呼叫及來源重建／重播均通過。這一有界大階段結束，不代表算法已達極限。

第39輪[細搜尋分列快取](GPU_FINE_TILES_zh-TW.md)沒有改善原128／512設定：實際都在第1層停止，全部ROI已快取。該輪維持第38輪建議，現已由第40輪更新；`full_gpu_fine_mode=1`保留為過大ROI的研究選項。相同圖片改成stop0後耗時少10.1%／9.9%，但整體仍比原stop1及相同設定的混合方案慢。主／補充162次GT通過、GPU有序輸出一致，未改通用預設。

第38輪分塊選峰通過四場景、36程序／108次GT與有序結果驗收，完整GPU研究選項建議明確使用mode1，保留mode0作基準；GUI／混合預設不變。128／512粗選峰占GPU時間85%／91%，改善後主瓶頸轉為細搜尋。完整階段時間、RSS與額外3.74／8.60MiB暫存見[報告](GPU_TILED_PEAKS_zh-TW.md)。

第37輪整條灰階GPU流程已補齊，完整範圍、時間／記憶體／GT與配置限制見[報告](FULL_GPU_zh-TW.md)。預設仍保留混合路徑；不能再以第36輪的局部常駐結果代表整條GPU的性能。

第36輪已完成48程序／192次首次及正式呼叫，另保留暖機，見[Metal常駐粗搜尋報告](COARSE_RESIDENT_zh-TW.md)。六組場景最終輸出均與原路徑一致；8K少物件255.17→187.88ms，但128物件834.79→4993.26ms、512物件2373.64→26361.99ms。RSS均較低；大量候選的GPU逐次選峰成本抵銷收益，不改建議設定。這只完成粗NCC正規化／選峰常駐，仍非全流程GPU，也沒有CUDA實測。

第35輪已完成500程序／1000呼叫，正式數字見[密集RGB場景報告](STAGE35_REAL_RGB_zh-TW.md)。小模板正常控制4/49→49/49，但25.58→100.28ms；另一個heldout模板原來49/49，調整只增加時間。線性色度找出兩個異色控制，但白平衡控制各誤報49個，VisA保留集三張異常全部漏搜。49物件半合成控制與FSC實拍、VisA實拍分開判讀；FSC類別點標註不是同一模板的身份GT，VisA也沒有完整物件姿態GT。

原核心與GUI預設保留。小模板較淺金字塔與顏色驗證可供研究比較；不把控制場景成功升格成所有實拍都可靠。RGB三通道不保證GPU必然更快，少量候選尤其需要看完整流程與初始化成本。

## 保留但不推薦直接替換的方案

- 整條Metal灰階常駐不作通用預設：第40輪peak1／fine4已可與混合競爭，但512與部分小圖仍較慢；第41輪換新影格時同樣是128與8K較快、512與六物件較慢。依相同工作量比較選用。
- 完整GPU來源統計滑動重用fine3：本輪初測與診斷較慢；保留源碼，不採用為推薦組合。
- Metal常駐粗選峰mode2：第36輪大量候選大幅退步；保留作分塊並行與未來CUDA的對照，不當通用預設。
- Fourier／log-polar提案：仍有裁切與背景反例，NumPy FFT尚未全部改為C++。
- 自適應NCC矩形上界：結構模板可加速，但隨機模板及完整128流程有退步，未採用為金字塔預設。
- fine相鄰統計重用mode1、稀疏前段合併提交、粗搜尋CPU／GPU重疊：部分場景變慢或多用記憶體，保留完整失敗。
- 遮擋／相似負例的單純擴大搜尋預算：第34輪未改善召回／身份區分，拒絕採用該方案。
- RGB NCC直接當異色判斷、白平衡未校正的色度直接當缺陷判斷：尚未通過實拍部署門檻。
