# 目前建議使用的方案

更新：2026-10-26（第49輪），Apple M4 Pro／48 GiB。這是依已測場景選型的指南，不是通用最快或完整實拍驗收證明。第一次閱讀請先看[專案導覽](../../docs/PROJECT_GUIDE_zh-TW.md)。第1–34輪詳細數字已移至[歷史建議](CURRENT_BEST_HISTORY_zh-TW.md)，避免把當年的「下一步」誤認成現在的待辦。

## 依使用場景選擇

| 使用情境 | 目前建議 | 採用界線與依據 |
|---|---|---|
| 一般灰階模板比對／Qt GUI | 先使用既有 CPU 基準與已實作旋轉、金字塔、subpixel | 穩定核心是固定尺度；需要尺度時選原生研究流程。GUI 預設未被實驗自動改動 |
| 大量相同模板、多尺度 | Metal 前段＋resident0精修、u8／shared、fine strip＋融合 | 第34輪同前段 CPU／Metal 公平比較，128／512物件完整時間約快12%／15%；不是全GPU |
| 完整解析度 subpixel 細搜尋 | 在上述組合評估精確角度重用 | 第29／30輪有收益；快速 stopLayer1 不一定重用得到 |
| 小圖／少候選／小模板精修 | 保留 CPU 精修選項 | GPU 啟動與同步可能超過計算收益，不能單由圖大小決定後端。[第45輪](CPU_PATH_zh-TW.md)全CPU路徑（搜尋也在CPU）在六物件每影格為191.32ms，比混合62.13ms與完整GPU k3 42.14ms都慢（6/6）；只換精修時六物件CPU只慢9% |
| 固定尺度、角度改變、大圖稀疏目標 | 可試方向特徵稀疏研究路徑＋Metal前段 | 第20輪4K優勢明顯；小圖仍CPU較快。這條路徑與金字塔模式分開比較 |
| 很小的細紋模板，旋轉後漏搜 | 先限制金字塔深度，檢查粗搜尋候選 | 第35輪發現43×30模板縮到11×8時漏搜；不能只降低最終接受分數。完整結果見第35輪報告。[第49輪](ADAPTIVE_PYRAMID_zh-TW.md)只看模板自動選頂層的`pyramid_rule`未通過（保留集回收0/111、30個足夠模板改淺11個），不要用它取代手動檢查；同一模板成敗取決於場景背景對比，需在實際影像上確認 |
| 定位後找顏色不同的物件 | RGB NCC與線性色度為研究選項；照明會變且模板有印刷中性區時，研究用`chroma_vk`（物件內白參考＋von Kries，常數模型）配第47輪原稿決定的 catch 門檻，棄權交人工檢查 | RGB NCC不保證異色可分；色度會受白平衡影響，實拍漏搜也無法由後段修復。[第46輪](ILLUMINANT_CHROMA_zh-TW.md)：`chroma_vk`在測試樣本集 v1 的 376 個異色（含 isogray）誤收 0，但事前的第 95 百分位門檻太緊，保留照明同色只接受 31/88，面板裁切時棄權；未通過事前門檻。[第47輪](CHROMA_MARGIN_zh-TW.md)：catch 門檻在新保留集有判定同色 57/57、ΔE≥4 異色 0/134，通過；局部暖光 11/20、過曝全部棄權，只在渲染資料驗證 |
| 粗搜尋正規化與選峰留在GPU | `coarse_peak_mode=2`僅供研究，維持`1`為建議值 | 第36輪8K少物件快26.4%，128／512物件耗時約6／11倍；完整源碼與失敗保留 |
| 完整灰階搜尋留在GPU | 研究設定選`full_gpu=true, full_gpu_peak_mode=2, full_gpu_fine_mode=4`（`full_gpu_peak_batch`預設8；設1不增加記憶體） | [第42輪](GPU_PARALLEL_PEAKS_zh-TW.md)：輸出與peak1逐位相同，128／512完整GPU時間再少27.3%／34.4%；每換新影格比混合快31.4%／22.7%，8K快80.1%，六物件混合仍快1.5%（[第44輪](DEDUP_PEAK2_zh-TW.md)同建置重測為−0.5%、3/6 block，無方向）；批次8多23／46MiB命名Metal配置。不含RGB與稀疏路徑 |
| 大量相同物件、可接受輸出不逐位相同 | 完整GPU peak2／fine4再加研究選項`candidate_dedup_top_k=3`（radius 0.5、angle_steps 3）；需要混合路徑時k3同樣可用 | [第44輪](DEDUP_PEAK2_zh-TW.md)同建置：完整GPU peak2上k3再少35.5%／38.9%（128／512靜態，6/6）；每換新影格時完整GPU k3在128、512、六物件都是四種組合中最快（384.13／1149.05／41.91ms，對混合k3 −39.0／−27.2／−11.4%），8K上k3無差別。[第43輪](CANDIDATE_DEDUP_zh-TW.md)與第44輪的GT案例變體零GT退步；會改變語意，matches不保證與基線相同。k1會失去物件；對稱週期小於3個粗角度步的模板未驗證。預設仍為0 |
| 同模板持續輸入新影格 | `Session::updateSource` | 保留模板與frame容量，每個Session同時只供一位呼叫者；不是直接重用舊影格金字塔。混合每次換影格會重建pose context（[第41輪](NEW_FRAME_COST_zh-TW.md)128約20ms、512約40ms）；[第48輪](FRAME_OVERHEADS_zh-TW.md)此外只多約1ms精修。影格之間若CPU與GPU都閒置65–131ms，這台機器上下一張混合多約31–42ms、完整GPU多約6ms（8K幾乎都是主機端上傳，512約一半是上傳與編碼、一半在等待GPU；8K fine4在閒置30ms、peak2在10ms就出現） |

> 2026-10-19更正：上表完整GPU對混合的比較中，混合正式呼叫重用首次建立的pose context；加回後fine4在128約快4%，512仍以混合較快。8K是常數背景上6個0°、尺度1的完全複本，屬精度鑑別力低的速度負載。見[第40輪報告文末更正](GPU_NCC_CLOSURE_zh-TW.md)。

> 2026-10-19第41輪實測：每次呼叫都換新影格（`updateSource`）時，fine4對混合每影格為128 −6.9%、512 +13.7%、六物件 +13.3%、8K −70.2%，各6個block同向，上一則估算的方向成立。持續輸入新影格時依此工作量選擇；預設不變。見[每影格成本](NEW_FRAME_COST_zh-TW.md)。

## 大量物件的原生研究設定

下列是第32／34輪支持的手動組合，鍵名採研究 runner JSON。它們不是 GUI 已自動啟用的預設，也沒有自動選型門檻。

```json
{
  "backend": 1,
  "refinement_backend": 1,
  "pose_resident_mode": 0,
  "pose_input_mode": 1,
  "pose_storage_mode": 1,
  "ncc_mode": 2,
  "coarse_peak_mode": 1,
  "fine_ncc_mode": 2,
  "fine_fused": true,
  "fine_angle_reuse": true,
  "overlap_enabled": false
}
```

尺度清單、角度範圍、模板大小、候選預算與接受分數仍須依任務設定。不同位置的 mode2 指不同功能：粗NCC空間重用、fine點積載入重用與resident SIMD精修不能混為一談。多尺度目前保留resident0；不能直接把固定尺度稀疏路徑的resident2優勢外推。

`pose_input_mode=1`減少初始化float暫存；`pose_storage_mode=1`共用CPU／Metal影像頁面。這是記憶體改善，不能把兩個不同輪次的加速率相乘。GPU共用頁面也不能再加到RSS，當成另一份實體記憶體。

## 本輪的採用判斷

第49輪[依模板資訊量選擇粗搜尋頂層](ADAPTIVE_PYRAMID_zh-TW.md)：預設關閉的研究選項`pyramid_rule`（門檻0.50）在事前登錄後才產生的保留集上未通過，不推薦。兩個召回不足的模板（fsc2931b0 2/98、b1 83/98）規則保持原深度、一個都沒救回；30個原本足夠的模板改淺11個，包括第35輪heldout模板（98/98、時間1.49倍）。整體TP 3025/3136，等時間預算（256／0.40／200）3058、固定512 3040、第35輪手動3130，搜尋時間總和分別為規則3004.7、預算3036.5、固定512 3862.6、手動6237.5、原設定2190.6ms（3022 TP）。各組正、負場景FP都是0。事後診斷：不足模板的場景背景在模板平均3.51／2.59個標準差之外，超出規則假設的±2；背景在範圍內的模板又被太悲觀的預測改淺。小模板漏搜仍以手動限制深度或放寬候選預算處理，並在實際影像上檢查；不改任何預設。

第48輪[每換一張影格的額外成本從哪裡來](FRAME_OVERHEADS_zh-TW.md)是診斷輪：拆開換來源與呼叫間空檔後，換來源只多pose重建與約1ms精修；CPU忙著解碼的空檔幾乎沒有影響，但CPU與GPU都閒置的空檔會讓下一次呼叫變慢（混合+31.6–42.3ms、完整GPU在512與8K +5.6–6.9ms；8K幾乎都是主機端上傳，512約一半）；混合隨空檔變長而更慢，完整GPU在8K閒置10–30ms以上就多約5–6ms，之後不再增加。即時串流若影格之間有閒置，應把這段喚醒成本算進每影格預算；研究建議與預設不變。

第45輪[全CPU研究路徑對混合與完整GPU](CPU_PATH_zh-TW.md)是量測輪：同一建置每換一張影格，全CPU（`backend=0`、`refinement_backend=0`，8執行緒、UDOT點積）在128／512／六物件／8K為3235.08／10236.80／191.32／444.50ms，是六種組合中最慢；完整GPU peak2＋k3為383.90／1144.31／42.14／49.21ms（快78.0–88.9%），混合也快40.2–76.0%，全部6/6。CPU上k3省30.7–42.1%且GT中立，112個案例變體的嚴格計數與Metal混合相同。正式計時期間主機負載偏高，CPU與8K混合數值可能偏高2–7%，方向不變。研究建議不變：大量相同物件用完整GPU peak2／fine4＋k3；沒有Metal的平台只能走CPU，預設不變。

第46輪[物件內白參考的照明正規化同色驗證](ILLUMINANT_CHROMA_zh-TW.md)：新的研究方法`chroma_vk`以模板米白面板經位姿映射後的每通道中位數估光源、做 von Kries 對角校正，再只在色彩區比較區域色度。在測試樣本集 v1 的事前登錄切分下，376 個異色物件（含 134 個灰階相同的 isogray）誤收 0，既有遮罩色度在保留照明誤收 63/192。但單類別第 95 百分位門檻只有 0.00039／0.00137／0.00094，保留照明同色只接受 31/88：白平衡偏暖 18/20 通過；局部暖光 4/20、JPEG 4/20、Blender 暖光 3/4、混合光 2/4 未通過；過曝時面板裁切，全部棄權。依事前規則不推薦，不改任何預設；既有`chroma`／`rgb_ncc`／`gray_ncc`輸出與改動前逐位相同。18% 灰參考卡在均勻照明下 57/80、0 誤收，但局部暖光 0/20。

第47輪[有餘裕的事前門檻與物件內光梯度模型](CHROMA_MARGIN_zh-TW.md)：`chroma_vk`的門檻改由標籤原稿決定，τ＝必須抓到的 ΔE00=4 變化（固定 L* 圓與 ΔE≥4 原稿變體）無雜訊最小區域色度距離的一半，紅 0.00816、藍綠 0.01470；第46輪校準照明只做 τ/2 可行性檢查。以從未用過的 layout／noise／background／Blender 種子重產的保留集上，主方法 `vk_region` 有判定的同色 57/57 接受，ΔE≥4 異色 0/134、isogray 0/52 誤收，事前 17 項判定全部通過，**推薦為 `chroma_vk` 的研究用門檻規則**（棄權是需人工檢查的輸出）。門檻外 ΔE 2 有部分被接受（保留照明 4/192），lightness+ 全部拒絕。覆蓋率是剩下的缺口：局部暖光 11/20 同色因面板裁切棄權（端到端 9/20），過曝全部棄權。同一批物件上，校準雜訊的 Rayleigh 規則有判定同色只接受 43/57、第46輪的 p95 規則 34/57。選用的線性光源模型（`reference_model: "linear"`）藍綠校準可行性未通過、梯度場景配對殘差反而較大（4／9，p=0.954），不推薦。不改任何預設；第46、47輪於2026-10-26一起併入main。

第44輪[去重疊在平行選峰上的實際速度](DEDUP_PEAK2_zh-TW.md)是量測輪，不改演算法。同一建置、8個arm（靜態與每換新影格×混合與完整GPU peak2×off與k3）、6 block：完整GPU peak2的k3對off靜態128 580.66→374.57ms（−35.5%）、512 1870.81→1143.71ms（−38.9%），達成事前10%目標；每換新影格時完整GPU k3在128、512、六物件對其他三組都6/6較快，8K上兩組完整GPU相同、都比混合快約80%。79個GT案例變體零退步，正式與GT每次呼叫的輸出都與第43輪封存相同。依事前規則，大量相同物件且可接受輸出不逐位相同時，研究設定建議完整GPU peak2／fine4＋k3；要求逐位相同時仍用peak2／fine4、去重關閉。GUI與預設不變。

第42輪[完整GPU粗選峰平行回合](GPU_PARALLEL_PEAKS_zh-TW.md)：`full_gpu_peak_mode=2`以精確平行回合與8張分數圖同批取代逐次選峰，完整有序輸出與peak1逐位相同。fine4靜態時間128 807.81→587.22ms、512 2868.42→1881.34ms，六物件−10.5%、8K−22.9%，皆6/6同向並達事前10%目標；每換新影格對混合為128 −31.4%、512 −22.7%、六物件+1.5%、8K −80.1%。peak RSS不變，命名Metal配置多23.26／45.74MiB。1538次直接GT零FP／FN、0筆失敗門檻；完整GPU研究建議改為peak2／fine4，GUI與混合預設不變，完整GPU仍是明確研究選項。

第41輪[每換一張影格的成本](NEW_FRAME_COST_zh-TW.md)只做量測：每次呼叫都經過`updateSource`時，fine4在128為808.35ms、比混合868.05ms快6.9%，512為2806.40ms、比混合2467.33ms慢13.7%，各6/6 block同向；六物件慢13.3%、8K快70.2%。混合每影格重建pose context中位19.94／40.19ms，另有候選搜尋的額外時間。96程序、1008次直接GT零FP／FN；不改GUI或通用預設，fine4仍是明確研究選項。（2026-10-26註：第48輪在macOS 27沒有重現候選搜尋的額外時間。）

第40輪[精確NCC與大階段結案](GPU_NCC_CLOSURE_zh-TW.md)完成有界uint32、來源統計滑動重用與SIMD32比較。GPU研究推薦peak1／fine4，完整時間128為806.46ms、512為2805.18ms；命名GPU配置不增加。統計重用mode3較慢，保留源碼與失敗。562次直接GT零FP／FN、GPU有序結果一致，Release70／70、五分鐘108次呼叫及來源重建／重播均通過。這一有界大階段結束，不代表算法已達極限。

第39輪[細搜尋分列快取](GPU_FINE_TILES_zh-TW.md)沒有改善原128／512設定：實際都在第1層停止，全部ROI已快取。該輪維持第38輪建議，現已由第40輪更新；`full_gpu_fine_mode=1`保留為過大ROI的研究選項。相同圖片改成stop0後耗時少10.1%／9.9%，但整體仍比原stop1及相同設定的混合方案慢。主／補充162次GT通過、GPU有序輸出一致，未改通用預設。

## 保留但不推薦直接替換的方案

- 整條Metal灰階常駐不作通用預設：第40輪peak1／fine4已可與混合競爭，但512與部分小圖仍較慢；第41輪換新影格時同樣是128與8K較快、512與六物件較慢。第42輪peak2後換新影格時128／512／8K都較快，六物件仍以混合略快；第44輪同建置重測六物件為無方向（−0.5%），加上k3後完整GPU在128／512／六物件都最快。仍依相同工作量比較選用。
- 完整GPU來源統計滑動重用fine3：本輪初測與診斷較慢；保留源碼，不採用為推薦組合。
- Metal常駐粗選峰mode2：第36輪大量候選大幅退步；保留作分塊並行與未來CUDA的對照，不當通用預設。
- Fourier／log-polar提案：仍有裁切與背景反例，NumPy FFT尚未全部改為C++。
- 依模板資訊量自動選粗搜尋頂層`pyramid_rule`（第49輪）：只看模板預測頂層NCC，保留集回收0/111、足夠模板改淺11/30，少於等時間預算與固定512的TP；保留源碼、預設關閉。
- 自適應NCC矩形上界：結構模板可加速，但隨機模板及完整128流程有退步，未採用為金字塔預設。
- fine相鄰統計重用mode1、稀疏前段合併提交、粗搜尋CPU／GPU重疊：部分場景變慢或多用記憶體，保留完整失敗。
- 遮擋／相似負例的單純擴大搜尋預算：第34輪未改善召回／身份區分，拒絕採用該方案。
- RGB NCC直接當異色判斷、白平衡未校正的色度直接當缺陷判斷：尚未通過實拍部署門檻。
- `chroma_vk`的第46輪設定（第 95 百分位單類別門檻）：分得開但門檻無法轉移到 JPEG、局部光梯度與 Blender 混合光；參考裁切時棄權後改用未校正距離的後備政策會誤收異色，不可使用。
- `chroma_vk`的線性光源模型（第47輪）：外插放大面板雜訊，校準可行性藍綠未通過，梯度場景殘差反而較大；只用校準雜訊的 Rayleigh 門檻在 JPEG、局部暖光與 Blender 混合光未通過。
