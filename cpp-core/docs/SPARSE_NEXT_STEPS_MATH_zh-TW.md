# 稀疏方向搜尋的下一步：等價壓縮、記憶體分塊與 GPU 邊界

2026-10-14。分析基準為 `70727a8`，程式為 [sparse_orientation.cpp](../experiments/sparse_orientation.cpp)，既有實測見[第16輪報告](SPARSE_ORIENTATION_zh-TW.md)。本文是數學推導與待驗證建議，不把配置減量當成已量到的速度或 RSS 改善；後續實作與正式量測已另存[第17輪等價壓縮實測](SPARSE_COMPACT_zh-TW.md)，其中來源表示減量已驗證，速度收益不是所有場景皆成立。

目前仍有明確改善空間。上一輪128物件案例的總時間中位數22.48 ms，來源方向圖準備9.45 ms、掃描3.02 ms、完整 NCC 精修9.58 ms；原先密集旋轉搜尋已不是此新路徑的主要成本。第一步應減少來源表示的建立與搬運，第二步才決定 GPU 的工作邊界。同時必須保留候選召回的失敗，不能用最終 NCC 成功掩蓋提案階段的風險。

## 1. 八張方向回應圖可以精確改成一張 byte 圖

令來源像素數為 `N=W×H`，強梯度方向量化為 `q(x)∈{0,…,7}`。弱梯度用零表示，其餘用單一 bit：

```text
B(x) = 1 << q(x)    若梯度強度通過門檻
       0            否則
M(x) = OR { B(x+d) : d∈[-r,r]² 且 x+d 在影像內 }
```

`M(x)` 記錄鄰域中出現過哪些方向，最多256種集合。對模板方向 `b` 定義2048-byte查表：

```text
C(b,k) = round(255 × |cos((b-k)π/8)|)
L[b,0] = 0
L[b,m] = max { C(b,k) : m 的第 k bit 為1 }
```

基準程式先算 `M`，再建立八張 `R_b(x)=L[b,M(x)]`。掃描時每個特徵讀取 `R_b(x)`。所以可以直接改為讀 `M(x)`，再取 `L[b,M(x)]`，不需要實體化全部 `R_b`。對每個 `b` 和每個可能的 `m`，新舊回應逐值相等，因此同一候選的整數總分也相等：

```text
P(t,θ) = Σᵢ L[bin(αᵢ−θ), M(t+round(Rθuᵢ))]
S(t,θ) = P(t,θ)/(255F)
```

只要保持方向量化、角度／座標取整、掃描位置、候選排序和去重規則不變，這項表示轉換不改變提案。整數上界剪枝也不變：已計 `j` 點、部分和為 `p_j` 時，若 `p_j+255(F−j)<ceil(τ×255F)` 就能排除。當前 `F≤4096`，總和最多1,044,480，uint32足夠。

**這是既有量化稀疏分數的精確等價；不是對完整 NCC 的精確替代。** 稀疏取點、方向量化、位置步距、角度採樣、選峰和候選上限原本具有的近似與漏檢風險都還在。也不能從方向分數導出完整 NCC 的安全排除界。

OR 的結合律與交換律還保證方形鄰域可分成水平、垂直兩次：`OR_y OR_x B(x+dx,y+dy)`，邊界使用同一裁切規則即可。這也是目前實作採用的分離式擴散。

| 只計來源表示的 byte payload | 八圖基準 | 一圖＋LUT提案 |
|---|---:|---:|
| 掃描期間來源表示 | `8N` | `N`，加2 KiB LUT |
| 原有三張暫存同時存活的建圖階段 | `11N` | `3N`，加LUT |
| 1536×768的掃描表示 | 9 MiB | 1.125 MiB |
| 同尺寸建圖階段payload | 12.375 MiB | 3.375 MiB |

這不包含來源像素本體、各執行緒score grids、候選、pose buffers與配置器；不能直接把表中差值當作程序peak RSS的差值。新方法移除八張圖的 `8N` bytes輸出寫入及對spread圖的展開讀取，但每次特徵評分增加一次依賴式LUT讀取。掃描的來源byte讀取指令數沒有因此變成八分之一；改善來自較小工作集與省去展開，實際cache miss和頻寬仍須量測。

LUT只有2 KiB，容易被cache重用，但C++不能保證它永久留在L1。若未來移至GPU，應將同一張整數LUT傳入，避免GPU重新用浮點cos生成而產生取整差異。2048個表值應完整驗證，新舊整條提案和完整NCC有序輸出也應比較。

## 2. 還有兩個可以單獨驗證的等價優化

**來源方向的有限輸入查表。** 灰階8-bit中央差分為 `g=(dx,dy)/2`，`dx,dy`都是 `[-255,255]` 整數。因此 `orientationBin(atan2(dy/2,dx/2))` 只有511²種輸入，可以在模型／程序初始化時計算成261,121-byte表，約255 KiB，每像素避免一次atan2。保留原梯度強度門檻，並對所有261,121組與原函式逐值驗證，尤其半bin、反相與零向量；零梯度因正門檻不會被採用。此表比2 KiB回應LUT大很多，額外查表可能受cache影響，不能在未測量前認定比atan2快。冷啟動成本也要獨立列出。

**串流擴散與小型輸出tile。** 水平OR的結果只需保留垂直鄰域所需的 `2r+1` 行，理論上可把部分全圖暫存改成環形列緩衝；與gradient計算融合時必須保持原邊界和行生命週期。掃描則把同一角度相鄰位置放在小型輸出tile，依相同特徵順序累加，讓相鄰位置讀取接近的來源座標。這些是不同變因，應先驗證compact表示，再分開測串流建圖與tile掃描。

若輸出tile有 `B_x×B_y` 個中心、網格步距為 `d`，旋轉後特徵偏移的座標跨度為 `h_x,h_y`，所有讀取落在最多

```text
[d(B_x−1)+h_x+1] × [d(B_y−1)+h_y+1]
```

個來源byte的包圍區域內，加2 KiB LUT及累加器。這只是工作集的包圍上界；特徵稀疏時，實際需要的聯集遠小於矩形，將整塊矩形全部搬入threadgroup可能浪費工作。先比較直接buffer讀取與tile遍歷，再考慮顯式staging。這延續[原NCC分塊研究](NCC_TILING_AND_OVERLAP_RESEARCH_zh-TW.md)的資料重用原則，並非直接套用attention公式。

## 3. GPU 適合整批工作，但只搬建圖不一定划算

梯度、水平OR、垂直OR皆可按像素平行；每個角度／位置的稀疏整數加總也可獨立。候選數與有效位置雖然動態，仍可用固定上限buffer、有效計數與批次描述來表達，不構成GPU無法處理的理由。

可先試每thread處理一個搜尋位置，各thread在同一步讀同一模板特徵；鄰近thread的來源位置相隔網格步距，具有空間局部性。每16個特徵的精確提前排除會讓threads退出時間不同，可能產生分歧。應比較保留早退與固定全點累加，分開記錄特徵評估數和device time；運算較少不一定執行較快。局部選峰、跨角度去重、空間配額的排序契約也必須保留，不能只換成任意GPU top-K。

若只有建圖搬到GPU，流程會變成：

```text
CPU來源 → GPU建圖 → 等待完成 → CPU掃描／選峰 → GPU精修 → CPU最後驗分
```

Apple shared memory可以避免部分實體拷貝，但CPU不能在GPU完成前讀結果，因此多出一道GPU→CPU依賴。端到端收益的必要比較是：

```text
CPU建圖時間 > GPU建圖＋提交／同步＋額外配置或拷貝＋CPU後續讀取變化
```

這裡wait與device time可能重疊，不能直接把兩者相加；應用牆鐘時間與timeline確認。更完整的研究邊界是 `建圖→掃描→選峰／候選壓縮→常駐NCC精修` 留在GPU，最後只回傳少量結果。先保留CPU版本與分段數字，避免為了「全GPU」增加小場景延遲。

## 4. 先用時間占比決定投入順序

對串行部分，若某階段占比為 `f`、它自身加速 `s` 倍且其他成本不變，Amdahl模型為 `speedup=1/[(1−f)+f/s]`。套用上一輪128物件的中位數作粗略預算，建圖占 `9.45/22.48≈42%`，即使整個建圖成本都消失，總體也約有1.73倍的模型上限；compact只消除其中一部分，更不能承諾這個倍數。掃描僅3.02 ms，單獨把掃描降至零的模型上限約1.16倍。

各階段中位數不必精確相加等於總時間中位數，上述是改善預算，不是新方法的效能預測。有重疊、頻寬競爭或候選數改變時，要重建模型並重新量測。完整精修仍占9.58 ms，且粗候選品質會影響它的迭代和救援成本；因此純看proposal kernel無法決定最後方案。

## 5. 建議的三個優先方向

2026-10-15補充：第18輪已完成目前工作負載的[CPU／Metal後端對照](SPARSE_CPU_METAL_zh-TW.md)，固定候選與精度條件下多數場景CPU較快，128物件打平。據此先採CPU，接著單獨驗證方向查表／串流建圖；這尚不是完整候選批量曲線或硬體等待歸因，也未實作表中的連續GPU資料流。

| 優先 | 工作 | 必須驗證的條件 |
|---|---|---|
| 1 | 一張mask＋LUT的等價表示；再各自試方向查表與串流建圖 | 新舊有序提案和最終結果一致；時間、RSS、配置容量與冷啟動成本分開 |
| 2 | 以實測分界安排CPU／GPU；先量不同候選批量，GPU試連續多階段 | 整體時間、device／wait／拷貝、資源生命週期；小圖不能因額外提交而退步 |
| 3 | 加入複雜背景、相近物件／遮擋與新實拍真值，再調候選策略 | 提案召回、最終FP／FN、角度／位置誤差、候選上限壓力與精修成本 |

第16輪128物件已用滿256候選，有一個真值不在事前6px／6°提案鄰域，最後由NCC恢復；這個失敗應保留。提高candidateCap或縮角度步距可能改善召回，也可能增加精修時間，必須是獨立實驗。不要改容差將既有失敗改寫成通過，也不要讓性能改善延後精度驗證。

## 6. 先前數學與其他研究建議如何銜接

Hinterstoisser等的方向擴散、回應圖與依掃描步距重排記憶體，直接支持這條研究路線；論文還包含RGB最強梯度通道、局部量化穩定化和深度模態。我們目前是灰階中央差分、分散選點與自訂候選策略，沒有完整移植LINE2D／LINEMOD。上述compact表示是依本專案程式逐式推導的等價改寫，不能把論文的辨識率或速度當成本專案結果。[Gradient Response Maps for Real-Time Detection of Texture-Less Objects，2012](https://vincentlepetit.github.io/files/papers/comp_hinterstoisser_pami12.pdf)

FFT仍適合作為大模板密集搜尋的另一條研究線：將NCC分子轉成相關運算，並一致計算局部正規化；旋轉遮罩下的完整推導已留在[固定尺度設計](FIXED_SCALE_SEARCH_DESIGN_zh-TW.md)。現有稀疏提案每個位置只處理少量點，又有提前排除，不能直接用密集相關的複雜度估計斷言FFT一定較快。[Lewis：Fast Normalized Cross-Correlation](https://scribblethink.org/Work/nvisionInterface/nip.html)

Steerable filters提供以基底線性組合合成方向濾波器的方法；對任意實拍模板的有限基底近似，仍須測截斷誤差、旋轉遮罩與NCC分母一致性。[Freeman、Adelson：The Design and Use of Steerable Filters](https://people.csail.mit.edu/billf/steerpaper.html) 旋轉NCC的對稱張量方法也值得另立原型，但論文結果不能直接當成2D Metal收益。[Almira等：Fast Normalized Cross-Correlation for Template Matching with Rotations](https://arxiv.org/abs/2311.07561)

這幾條方法處理不同問題：compact與分塊減少表示／資料流成本；FFT減少密集平移相關成本；旋轉基底嘗試減少角度枚舉；GPU把已形成的規則工作批次並行。最合理的順序是先做低風險、可逐值驗證的表示改善，再用新的瓶頸決定更大型的數學改寫。
