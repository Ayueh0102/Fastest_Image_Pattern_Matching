### 記憶體：已能從源碼定位的配置點

以下為配置路徑的靜態檢查，**不是已量出的 RSS 歸因或保證可回收的數字**。8192×8192 的 gray8、RGB888、float32 單通道邏輯像素容量分別為64、192、256 MiB；這些容量不能再與 RSS 直接相加。

- 第31輪GUI與原生runner已對明確Grayscale8解碼直接保留灰階，其他格式沿用RGB888與原係數。第32輪再獨立驗證精修共用影像及直接8-bit入口於多尺度512流程；不要把兩個階段的RSS差直接相加。
- `Session` 持有來源副本，`frame.prepare` 另建立來源金字塔第0層；這保證外部資料改動與非同步生命週期安全。減少副本必須保留明確的持有權與失效規則。
- 初次建立 pose 時，Session 建立 float 暫存，pose API 再複製進自有資料並中心化，storage0的Metal另建立buffer；第24輪storage1已共用CPU／Metal頁面，第25輪input1另移除Session float暫存，原input0保留。這是精修初始化的配置點；前一輪8K場景只執行離散搜尋（core-only），不能拿 pose 配置來解釋該8K結果的記憶體差額。
- GUI 還有視窗、繪圖與上一份工作結果的持有關係；原生 runner 的 RSS 不能當作整個 GUI 程序 RSS。必須另量換圖、切換模式與閒置時的資源釋放。
