# Stage35：真實郵票素材暴露的金字塔漏檢診斷

日期：2026-10-17。這份文件記錄正式測量前的 pilot，方便外部 reviewer
區分整合程式錯誤、既有演算法限制，以及為本輪選定的研究設定。

**結論：新色彩 runner 沒有改錯搜尋結果；小郵票模板縮得過小時，既有
CPU 與 Metal 搜尋都會漏掉正確候選。減少一層金字塔後，49 物件控制圖
可全數找回。這項改善沒有讓真實膠囊場景通過驗證。**

本次未修改核心演算法或 GUI 預設。正式實驗採明確指定的研究設定，保留
原設定為對照。這份文件的單次時間不是正式效能排名。

## 1. 問題與資料範圍

`development_clean` 是從 FSC147 真實郵票照片裁出 43×30 RGB 模板後，
放置 49 個不同角度副本的**半合成控制圖**。幾何位置、角度、尺度來自
產生器；它不代表 49 個獨立實拍物件或 49 張獨立照片。

原設定是 `min_area=256`、`proposal_score=0.5`、`limit=100`，控制圖的
最終接受分數為 `0.8`。搜尋結果只有 4 個，成功角度集中在約 −86.6°、
−5.3°、94.6°、97.7°。同時，FSC2933 原圖甚至沒有找回從它裁出的模板。

FSC147 的官方點標註描述同類物件數，沒有提供「全部郵票都與同一個模板
完全相同」的標籤。因此，本診斷只把 FSC2933 的已知裁切原位當作自匹配
檢查；其他郵票結果不轉寫成完整的同模板召回率。

## 2. 先排除新 runner 整合錯誤

將新 runner 的 `search` 參數原樣展平，交給先前已存在的
`build/stage34-closure/experiments/fpm_native_pipeline_runner`。輸入圖片、
模板、尺度、角度、NCC 模式、精修與候選設定完全一致。

| 場景 | 新整合 runner | 原 Stage34 runner | 完整匹配欄位是否一致 |
|---|---:|---:|---|
| development_clean | 4 | 4 | 完全一致 |
| fsc_2933 | 0 | 0 | 完全一致 |
| capsules_normal_000 | 1 | 1 | 完全一致 |

「完全一致」比較位置、角度、尺度、分數與角點，不只比較數量。將
`stop_layer` 單獨從 1 改為 0，三者仍是 4／0／1。

對 development_clean 與 FSC2933，改用 CPU 前段、粗搜尋 NCC 模式
0 或 1、停用細搜尋合併提交、停用角度重用，仍然得到 4／0。
因此沒有證據將問題歸因於新 JSON 解析、座標轉換，或某個 Metal
最佳化分支的數值錯誤。

## 3. 正確位置本身能否得到高分

另開獨立診斷，直接把產生器已知位置與角度交給既有 NCC 評分器：

- 控制圖 49 個正確 pose 的灰階 NCC 為 **0.951806～0.965071**，全部
  高於最終門檻 0.8。
- FSC2933 裁切原位的分數為 **1.0**。

這是 GT oracle 診斷，用來判斷「有沒有可辨識的高分解」。**這些 GT
pose 沒有送入正式全圖搜尋，也不能算成實際搜尋成功。**
證據表明，主要問題出現在候選產生／粗到細篩選，而非最終 NCC 在
正確位置必然得不到高分。

## 4. 金字塔與候選設定的有界比較

現有 `Pattern` 保留原演算法的面積除以四規則，以及
`floor(sqrt(min_area))²` 的門檻。對這個 43×30 模板：

| min_area | 實際模板層級 | 搜尋控制圖結果 |
|---:|---|---:|
| 256 | 43×30 → 22×15 → 11×8 | 4/49 |
| 512 | 43×30 → 22×15 | 49/49 |
| 1024 | 43×30 → 22×15 | 49/49 |
| 1,000,000 | 43×30，無降採樣 | 49/49 |

512 與 1024 對這個模板得到相同深度；這不表示它們對所有模板及尺度
都有相同行為。對控制圖，512 的 49 個結果分別對應 49 個不同 GT，
沒有用重複誤檢湊數。以位置 2 px、角度 2°核對時，最大位置誤差僅
**0.0385 px**，最大角度誤差 **0.2604°**。

以下都是原 Stage34 runner 的 pilot。每個設定只有首次呼叫及一次
後續呼叫；表中列後續呼叫時間，沒有足夠重複數估計分布或置信區間。

| 控制圖前段設定 | 唯一正確匹配 | 一次後續呼叫時間 |
|---|---:|---:|
| 原 256／0.5／100 | 4/49 | 26.0 ms |
| 512／0.5／100 | 49/49 | 83.4 ms |
| 1024／0.5／100 | 49/49 | 69.5 ms |
| 無金字塔／0.5／100 | 49/49 | 580.1 ms |
| 256／0.25／300 | 42/49 | 57.1 ms |
| **512／0.25／300** | **49/49** | **94.8 ms** |

表中的三個數字依序是 min_area／proposal_score／limit。1024 與 512
的單次時間差不能當作前者更快的證據，因為這裡兩者使用相同層級。
`limit` 是現有最大輸出數設定，也影響每個尺度的候選保留量；它不是
獨立的全尺度候選總上限。

FSC2933 在 512／0.5／100 下找到一張鄰近相似郵票，仍漏掉裁切原位；
改成 **512／0.25／300** 後，找到原位（分數 1.0）及一張相似郵票。
完全不用金字塔則有 3 個結果。這是選用較寬候選設定的理由。

有直接控制證據支持「金字塔過深與候選篩選導致漏失」。至於降採樣的
取樣相位、裁切邊界濾波、角度步距各自貢獻多少，尚未獨立分解；本輪
沒有宣稱已找到並修正一個 NCC 算術錯誤。

## 5. 本輪固定設定與保留對照

正式四路比較共用 `min_area=512`、`proposal_score=0.25`、`limit=300`
的灰階全圖搜尋，分別比較純幾何結果、RGB NCC CPU、RGB NCC Metal、
CPU chroma 驗證。各類場景既定的最終分數、尺度與其他參數保留不變。

第五路 `geometry_original` 保留原本 **256／0.5／100**，呈現改善前
速度與漏檢限制。這是研究 recipe，並未自動替換 GUI 或函式庫預設。
後續正式時間、記憶體與準確度應以正式報告為準，不拿本文件的
pilot 時間取代它們。

## 6. 真實膠囊仍未通過

只查看 development／校準資料，未用 heldout 影像調參。VisA 的
`normal_000` 是提供模板的自匹配控制，不參與色彩門檻校準。

| 正常實拍影像 | 512／0.5／100 候選數 | 512／0.25／300 候選數 |
|---|---:|---:|
| normal_000，自匹配 | 1 | 1 |
| normal_050，校準 | 0 | 0 |
| normal_200，校準 | 1 | 1 |
| normal_400，校準 | 0 | 0 |

放寬候選設定沒有改善這四張圖，第二組設定的單次後續呼叫約
274～284 ms。這些數字是候選數，資料沒有完整逐物件幾何標註，不能
直接轉成實拍物件召回率。

三張獨立正常校準圖僅 **1/3 可觀測到候選**，因此色彩校準只能標為
**provisional（暫定）**。沒有候選時必須保留 **abstention（無法判斷）**，
不可視為「正常」或「沒有異色缺陷」。新色彩驗證器也不能救回前段
沒有找到的物件。

膠囊的反光、透明材質、姿態造成的外觀差異，可能破壞單一平面模板的
假設；這是待研究解釋，沒有由本次控制實驗單獨證明。
**本輪半合成成功不等於真實泛化成功，真實泛化目前未過關。**

## 7. 外部 review 的證據入口

本機原始資料根目錄為 `build/stage35-real-rgb/pilot-diagnosis/`。
這些 build 路徑是工作資料位置，尚不能當作公共資料下載連結。

| 檔案 | 用途 |
|---|---|
| `native-comparison.json`、`compare_native.py` | 原／新 runner 一致性與 stop_layer 對照 |
| `fixed-gt-pose-comparison.json`、`fixed_pose.py` | GT pose 高分存在性診斷，與全圖搜尋分開 |
| `proposal-ablation.json`、`proposal_ablation.py` | CPU／Metal、NCC 模式與細搜尋選項排除 |
| `pyramid-ablation.json`、`pyramid_ablation.py` | 金字塔深度、門檻、候選保留量比較 |
| `development-geometry-audit.json` | 唯一 GT 配對、位置與角度誤差 |
| `capsule-bounded.json`、`capsule_bounded.py` | 四張正常膠囊圖的有界比較 |
| `*.job.json`、`*.raw.json`、`*.stderr.txt` | 每次原始請求、完整輸出與錯誤輸出 |

完整 runner 使用契約、NCC 正規化限制與計時／RSS 邊界見
[COLOR_VERIFY_RUNNER.md](COLOR_VERIFY_RUNNER.md)。原生回歸測試涵蓋
幾何與遮罩、無效支援、曝光與 NCC 色偏不變性；CLI 測試涵蓋整合搜尋
一致性、空候選、GT 輸入拒絕與 CPU／Metal RGB 分數一致性。

既有測試紀錄位於 `build/stage35-real-rgb/logs/`：
`color-test-release.log`、`color-test-asan.log`、`color-worker-contract.log`。
Release 與 ASan／UBSan 原生測試各通過 1/1，CLI 測試通過 5/5。
這些控制通過確認新增功能的契約，不能替代真實場景品質驗證。
