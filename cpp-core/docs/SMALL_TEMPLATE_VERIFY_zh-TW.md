# 小模板誤判：影像邊界重算與依尺寸的接受門檻（第52輪）

第52輪，2026-10-27，Apple M4 Pro／48 GiB，macOS 27。新增兩個**預設關閉**的研究選項，處理小模板（約 12–24 px）在空白與干擾場景的誤判。GUI、核心、研究流程與 CURRENT_BEST 的預設都不變。

**起因（第50輪 C 組）：** 完整 GPU k3 在微小模板負場景有 338 個誤判。
- **邊界誤判 189 個**：全部來自平滑漸層模板 `proc50105`。比對器沿用 MFC 原版，把影像外補成純黑或純白（`image.cpp:50`），模板可以有一部分落在影像外。結果影像邊緣和補值的明暗交界，被當成了漸層模板。
- **干擾物誤判 149 個**：分數 0.84–0.92；真目標的中位數是 0.986。

## 兩個檢查怎麼做

兩個都在 `cpp-core/experiments/match_verify.{hpp,cpp}`，透過 runner 的 job key 開啟，預設 0 表示關閉。

**邊界檢查 `border_min_inside`（固定 0.5，沒有調參）：**
- 只處理模板範圍超出影像的候選；完全在影像內的候選不重算。
- 模板像素 x 對應到 `center + scale·R·(x − w/2)`，R 是 `makeMatch` 的旋轉方向，來源像素中心在整數座標，用雙線性取樣。
- 只用落在影像內的像素重算 NCC。影像內占比低於 0.5，或重算的 NCC 低於最低分數，就剔除。
- 這套座標換算用第50輪 4510 個完全在影像內的匹配驗證過：重算分數和比對器回報的分數，差距最大 0.0018。

**尺寸門檻 `small_template_area` = A0：**
- 模板面積 area = w·h·scale²。小於 A0 時，要求分數 ≥ 1 − (1 − 最低分數)·√(area/A0)；大於等於 A0 時維持原本的最低分數。
- 以最低分數 0.8、A0 576 為例：12×8 的模板要 0.92，24×24 的模板維持 0.8。

**兩條路徑的差異：**
- CPU／混合路徑在 NMS **之前**檢查，被剔除的候選不會壓掉別的候選，也不會佔用輸出名額。
- 完整 GPU 路徑的 NMS 在 GPU 上，只能對**最後的輸出**過濾，被剔除的不會有別的候選補上。

**原本以為的風險不存在：** 選項關閉時，帶紋理的真物件只要有 20–30% 在影像外，比對器就已經找不到了，因為補成黑白的那塊會把分數拉低。實際會被找到的邊界候選，絕大多數就是漸層模板的假匹配。A 組的 `boundary_one` 物件四角在 (0,0)–(64,48)，整個在影像內，不受這條規則影響。

## 結果細節

**誤判集中在少數場景：** 不開時的 648 個誤判，只出現在 64 個負場景中的 13 個。
- 程序紋理的空白場景：225 個，全部在邊界。
- 程序紋理的干擾場景：419 個，其中 180 個在邊界。
- Dst 縮圖模板：只有 4 個。

**尺寸門檻掉的 14 個真目標（混合；完整 GPU 也是 14 個）：**
- 8 個在邊界切割場景，其中 5 個是跨出邊緣的那一圈。
- 6 個在 Dst 縮圖模板的乾淨／雜訊場景。

這些真目標的分數介於 0.8 和各自的尺寸門檻之間。

**多報的框也變少了：** 正場景中不是嚴格命中的輸出，不開時 749 個，兩個都開時 255 個（混合）。多半是同一物件旁的重複框，或貼邊的假匹配。

## 失敗與揭露（全部保留）

- **正式保留集第 1 次：** 主機檢查把驅動程式本身和啟動它的 shell 當成重工作，因為它們的命令列含有 runner 路徑。結果空等 51 分鐘後被停掉，沒有任何 worker 執行，也沒有寫出任何輸出。修正後改為排除自己的父程序鏈（`480269d`，protocol 修訂 1，`HostCheckTest`），從頭重跑。
- **冒煙測試：** 正式量測前跑了 3 個保留集案例 × 8 個 arm，只作描述，存在 validation-logs 的 `smoke/`。
- **回歸集沒有觸發任何剔除：** 196 次執行、開啟檢查時共檢查 4710 個候選，沒有一個超出影像，也沒有任何候選被剔除。這組案例的模板面積都 ≥ 576，也沒有超出影像的候選，所以逐位相同是預期中的結果。它只證明「沒觸發時路徑不變」，不能證明「大模板觸發時也無害」。
- **完整 GPU 是在輸出後才過濾：** 被剔除的匹配不會有別的候選補上。在這個保留集上，兩種後端的命中與誤判最多只差 1。
- **建置來源：** 正式 binary 在凍結 commit `bcd409d` 建置，ctest 91/91（`formal-build.json` 記錄了 CMakeCache 的來源目錄、`match_verify` 的目標檔與 runner 雜湊）。之後到正式量測之間只改了 Python 的主機檢查（`480269d`），封存的源碼快照就是這個 commit。
- **開發集就是第50輪的資料：** 只有保留集算證據。
- **Dst1、Dst2 的 16 px 版本很細長：** 分別是 16×5、16×4。

## 量測方法與界線

- **時間：** 每個保留集案例先暖機 0.3 秒，再量 3 次，取中位數；只跑一個區塊。時間除了 H6 之外都只作描述。
- **主機：** 正式量測期間持有 `timing-lock-round52-{holdout,regression}.txt`，並確認沒有別的鎖、也沒有別的**本專案**重工作在跑。主機檢查不看其他程式：保留集 1280 筆中有 352 筆在計時時另有程序佔用 CPU（rustc 222 筆、node 135 筆），load1 在 1.35–5.30 之間，見驗收補充。每個 worker 的主機狀態都記在 manifest。
- **評分：** 用第50輪的獨立評分程式 `literature_score.py`（嚴格位姿 2 px／1°／逐軸 2%，最大配對）。負場景的輸出全部算誤判；只要有一個角點超出最外圈像素中心，就算邊界誤判。
- **界線：** 只有一台 M4 Pro；全部是合成場景；穩定核心 `fpm_cli` 沒有這兩個檢查；保留集上沒有跑 TDCM 和 OpenCV，第50輪的 93／198 是另一批場景的數字。

## 怎麼用（研究設定）

小模板（大約 30×30 以下）在可能有空白、漸層或相似干擾的場景時，在研究 runner 的 job 加上：

```json
{"border_min_inside": 0.5, "small_template_area": 576}
```

- 只要擔心邊界誤判，可以只開 `border_min_inside`，它在保留集上沒有損失任何真目標。
- 尺寸門檻會讓分數剛好在 0.8 附近的小模板真目標被剔除，所以在曝光不足或嚴重模糊的影像上要先確認命中率。
- 大模板（面積 ≥ 576）不受尺寸門檻影響。
